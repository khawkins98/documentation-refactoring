# Repository-wide documentation work

Use for a broad rollout alongside the skill's [scope and authority](../SKILL.md#establish-scope-and-authority)
and [verification](../SKILL.md#verify-the-result) rules.

## Find homes before making copies

Inventory document families by path, purpose, audience and governing source.
Identify reader paths and competing accounts. Choose where each maintained
explanation lives, then route readers there. Reuse existing pages when they fit.
A small task index can connect families without making the README exhaustive.
Avoid a catalog that becomes another detailed description to maintain.

## Keep the work reviewable

For competing approaches, use the same baseline and comparable reader tasks.
Show both what becomes easier and what navigation becomes longer. If delegating,
assign disjoint file ownership or isolated branches and integrate deliberately.
Do not introduce parallel work unless authorized and worthwhile.

Check inbound links before deleting headings. Pointer pages or explicit anchor
aliases can preserve useful routes; unlimited compatibility stubs can recreate
sprawl. Select them based on actual callers and expected readers.

Document shared maintenance rules once and link from agent/contributor entrances.
A new API should update its appropriate reference and affected recipes; it should
not automatically expand every README. Keep local technical policies local.

## Choose proportionate safeguards

A manual map may suffice for a small repository. A repeatable inventory or audit
is useful when ongoing scale justifies it. If adding tooling, make limits explicit:
classification, word counts and link checks do not verify factual correctness.
For a documented helper affected by a UI/API migration, check the first action it
performs, not just that its file exists. A retired selector or storage key can
leave every link valid while the reader's task fails. Keep this source check
focused; it does not require running every asset-dependent capture pipeline.
Make size thresholds advisory unless the project explicitly adopts a hard limit.

## Report and iterate

Summarize the reader-facing changes, canonical homes, important factual fixes,
actual checks, known limitations and navigation tradeoffs. Keep unresolved facts
visible. Preserve detailed references where required rather than claiming every
page is now short.

Use real reader failures and repeated maintenance friction to improve the skill.
Before adding a rule, ask whether it generalizes or belongs in the affected
project. The [Scriptoscope case study](scriptoscope-lessons.md) illustrates this
distinction; read it when choosing safeguards or reviewing an iteration.

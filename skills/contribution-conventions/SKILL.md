# Contribution conventions

These are maintainer preferences, not universal repository requirements. Explicit
user instructions and the target project's rules take precedence. This skill
helps prepare the contribution requested; it does not authorize pushing, opening
a PR, merging, publishing or changing repository configuration by itself.

The specialist sources are **Conventional Commits contributors** and **dmythro
and contributors' git-commit skill**, combined with the maintainer's preferences.
For type lookup, use the [directly reused table](references/upstream/dmythro/commit-types.md).
Its [source record](references/expert-map.md) and [MIT notice](references/upstream/dmythro/LICENSE)
travel with this skill. Other workflow instructions are independently written.

## Inspect the actual contribution

Read applicable repository instructions, contribution guidance and PR templates.
Inspect the final diff and checks. Follow the project's branch/base, validation,
attribution and review requirements. Preserve unrelated work, existing human
credits, licensing and historical commit metadata. Do not rewrite history to
remove trailers or silently configure global Git behavior.

Validate the final base-to-head diff, not only unstaged edits. If the project
requires an exact-head readiness receipt, attach it for the final pushed candidate;
passing CI or a clean working tree alone does not establish that requirement.

## Titles and commits

When the project does not specify otherwise, use Conventional Commits for new
commits and PR titles: `type(scope): concrete result`, with scope when useful.
Use `!` or the required breaking-change footer only for an actual breaking change.
Choose the type from the resulting capability, not the file extension: adding a
new skill can be `feat`; correcting its instructions can be `docs`.
Match squash-merge titles to the project's automation. A different project title
scheme overrides this default.

Keep commits coherent and describe why/impact in a body when needed. Do not add
unsolicited `Co-Authored-By:` trailers, "generated by" signatures, tool branding or
permanent AI-credit boilerplate to newly written commits or PR descriptions.
Honor an explicit user/project attribution requirement, retain existing credits,
and do not misrepresent actual authorship. This default is about unnecessary
boilerplate, not removing people or license obligations.

## Pull request descriptions

Lead with the concrete problem and resulting behavior. Add implementation detail,
tradeoffs, actual validation and material limits in proportion to the change.
Use the repository template where required. Otherwise short prose is often enough;
headings or lists are useful only when they make the review easier. Conventional
Commit syntax applies to titles, not a special body format.

Use valid CommonMark: blank lines before lists and after headings, real newlines,
and readable links. For multiline CLI input, use a structured body argument or a
file such as `gh pr create --body-file <path>`; do not interpolate body text into
shell code. Write the description for a reviewer without conversation context.
Update the title/body if the final scope changes; omit abandoned approaches unless
they explain a tradeoff. Report only checks that actually ran.

If the user already authorized the draft PR or contribution, complete it without
asking for the same permission again. Keep draft/ready state as requested. Do not
infer permission to merge or release from permission to open a PR.
